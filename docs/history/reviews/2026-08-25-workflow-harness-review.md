# Review multi-agente — Harness de dynamic workflows da Lohra

## 1. Veredito

No caminho feliz, sim: os 7 node-types executam de verdade (pipeline no-barrier, verify/judge_panel, nesting, resume content-addressed), o orquestrador é determinístico por construção e o sandbox de leaf é mais forte que os substratos executores-de-código que substitui — 7/15 capacidades em paridade plena com o Claude Code, 7 parciais, 1 ausente. Sob falha, não: timeout não cancela o leaf (worker zumbi), `cancel` não cancela, `verify` falha *aberto* com todos os skeptics mortos, null de upstream vira a string literal `"null"` no prompt downstream, e rate-limit — o único "no" do scorecard — degrada o run em vez de pausar. O agravante sistêmico é que a falha é invisível: run 100% nulo reporta "complete" e a library certifica composto quebrado como template reusável. A suíte "verde" cobre só o happy path — os vereditos adversariais notam explicitamente que **nenhum** branch de falha (LEAF_TIMEOUT, done.wait expirado, skeptics mortos, resume-em-voo) tem teste.

## 3. Findings confirmados (verificação adversarial), por severidade calibrada

Ordenados pela severidade **pós-verificação** — dois foram rebaixados pelo próprio veredito adversarial, indicado abaixo.

1. **CRITICAL — `service.py:108` — resume de run ainda rodando clobbera o RunState e compartilha cache/workdir com o run vivo.** `self._runs[run_id] = state` sem checar liveness: o run original fica inalcançável por status/cancel (core órfão incancelável), e dois engines escrevem no mesmo `working_root` e nas mesmas linhas do `workflow_node_cache`. *Próximo passo:* em `start()`, sob o lock, rejeitar `resume_run_id` cujo estado não seja terminal.

2. **HIGH (rebaixado de critical pela verificação; critical só no caso stream-gotejante) — `engine.py:256` — timeout do collect não cancela o leaf: worker zumbi até starvation do pool.** `collect(wait=True, timeout=LEAF_TIMEOUT)` no timeout engole a exceção e nunca emite `cancel()`; o turno segue ocupando worker, spawns enfileiram, e `shutdown(wait=True)` bloqueia o chamador (inclusive a thread de tool do agente-pai via `workflow_cancel`). *Próximo passo:* no timeout, chamar `core.cancel(sub_id)` + timeout de rede nos clients + `shutdown` não-bloqueante.

3. **HIGH — `strategies.py:124` — `verify` falha ABERTO: todos os skeptics mortos ⇒ finding carimbado como verificado.** `counted=0` torna `kill and counted` falsy → `survived=True`, zero fault registrado — exatamente sob o modo de falha (429 sustentado) que o gate de rigor existe para pegar. *Próximo passo:* `counted == 0` (ou < quorum) ⇒ fail-closed com fault explícito no rollup.

4. **HIGH — `refs.py:68` — output nulo de upstream vira a string literal `"null"`/`"None"` no prompt downstream.** Leaf morto → `${gen}` interpolado como `"null"` (ref inteira → `str(None)`); a resposta confiante-e-errada do downstream é cacheada como completion e não incrementa null_count — contaminação invisível no rollup. *Próximo passo:* detectar refs resolvidas para None antes do spawn e nullar o node (ou registrar fault).

5. **HIGH — `strategies.py:99` — container `branches`/`attempts` como `${ref}` nunca é resolvido: vira `[]` silencioso e o run lê "complete".** A própria mensagem do fanout_cap manda o autor usar `${ref}` — direcionando pra armadilha; parallel retorna `[]` (não-None, sem fault) e `library.py:58` certifica o workflow quebrado como template. *Próximo passo:* resolver o container via `refs.resolve_value` (como `run_pipeline` já faz) e tratar não-lista como fault.

6. **HIGH — `core.py:214` — cancel não cancela (4 mecanismos compostos).** Interrupt só cooperativo (não acorda chamada LLM em voo), `shutdown(wait=True)` bloqueia a thread do pai, steers pendentes relançam turno completo pós-cancel, e pós-shutdown o engine segue criando linhas de sessão órfãs no DB. *Próximo passo:* flag de cancel checada pelo engine antes de cada node + `shutdown(cancel_futures=True)` assíncrono + checar interrupt antes de consumir leftover steers.

7. **MEDIUM (rebaixado de high pela verificação — exige node de pipeline >30min) — `strategies.py:275` — após `done.wait(PIPELINE_TIMEOUT)` estourar, on_done retardatários mutam `results`/rollup já publicados.** A lista parcial retornada é o mesmo objeto em `result.outputs`; retardatários mutam índices, gravam cache e contabilizam tokens num RunResult possivelmente já certificado pela library. *Próximo passo:* flag `expired` sob o lock local que faz `finish` descartar tardios + devolver cópia de `results`.

8. **MEDIUM (rebaixado de high pela verificação — requer stage que não interpola o item; garantido no resume) — `strategies.py:229` — cache key do pipeline omite a identidade do item.** `cell_hash(node.id, stage_idx, prompt, schema)` sem o item: stage cujo prompt não interpola `${item}` colapsa N itens numa célula (`INSERT OR REPLACE` guarda 1 linha); no resume, todos os itens recebem o output de um só — violando a spec (`07-workflow-harness.md:303`). *Próximo passo:* incluir `items[index]` cru no hash da célula.

## 4. Suspeitas (não verificadas adversarialmente — rotular como tal antes de agir)

Agrupadas por tema; nenhuma passou por verificação, tratar como hipóteses plausíveis lidas do código.

**Rollup cego a falha (o tema mais recorrente):**
- `engine.py:294` — run 100% nulo reporta "complete": status degrada só por `faults`, leaf morto vira null_count sem fault, e a mensagem de erro real do provider (`sub.output` com status=error) é descartada antes do rollup (aparece em 3 variantes nos materiais — é um único defeito).
- `strategies.py:251` — Nones *internos* de listas (pipeline/parallel) invisíveis ao null_count do nó: pipeline com 4/10 itens mortos vira template certificado; leaf morto no pipeline não tem retry (só schema-invalid tem).
- `strategies.py:237` — drop por lifetime esgotado no pipeline é só log de servidor + null (contradiz "caps nunca silenciosos").
- `strategies.py:180` — `loop_until_dry` trata leaf morto (None) como rodada seca e encerra prematuramente.
- `budget.py:1` — sem teto de tokens (docstring admite: "Milestone F"); run desgovernado só para em 1000 spawns.

**Superfície de ensino da tool:**
- `schema.py:44` — `SpecIssue.example` (o exemplo corrigido) nunca chega ao modelo: `ValidationError.message` o dropa.
- `tools.py:17` — RUN_GUIDANCE omite `pipeline` e `workflow`, zero enumeração de campos, zero exemplo.
- `strategies.py:311` — stages de pipeline são prompt-only e não-validados: o exemplo canônico da própria spec (`verify` como stage) roda silenciosamente como agent de prompt vazio.

**Campos declarados-mas-ignorados** (a mesma classe de footgun que o projeto já corrigiu para model/effort):
- `nodes.py:60/70/109`, `schema.py:251` — `min_success_ratio`, `required`, `budget` do loop e `inputs` passam na validação e não têm nenhum consumidor.
- `nodes.py:89` — `synthesize` obrigatório no validador, opcional no engine.
- `strategies.py:103` — schema/model/effort/provider ignorados em branches de parallel e stages de pipeline.
- `strategies.py:164` — schemas nomeados em synthesize/body não passam por `resolve_schema` (erro inútil ou skip silencioso de validação).
- `schema.py:170` — roots de contexto (`args`/`item`/`stage`/`winner`…) não reservados como node ids: shadowing, ciclos-fantasma, refs sempre-null.

**Races e lifecycle menores (core/service):**
- `service.py:121` — check-then-act entre `cancel` e `_run` sem lock: run cancelado pode virar "complete" e gravar prior/template (viola o invariante "run cancelada não grava prior").
- `core.py:261` — janela de steer perdido: enqueue após o drain final estranda o texto no inbox com `{"ok": true, "queued": true}`.
- `core.py:233` — eviction (cap 200) pode dropar leaf de pipeline completo antes do on_done coletar (256 spawns > 200 em pipeline 64×4).
- `strategies.py:345` — verify/judge_panel/parallel/loop nunca consultam o NodeCache: resume re-paga todos os leaves desses nodes.
- `service.py:132` — zero progresso vivo mid-run; `service.py:152` — sem pause/list/notificação.
- `cache.py:24` — `default=str` no `content_hash` é trapdoor latente (repr com endereço de memória) — hoje não disparado.

## 5. As 3 ações de maior alavancagem

1. **"Falha nunca é silenciosa" — um passe fail-closed no rollup.** Propagar erro de leaf como fault, derivar status de null_count (all-null ⇒ failed, parcial ⇒ degraded), contar Nones internos de listas, `verify` fail-closed com quorum, resolver containers-`${ref}` e tratar não-lista como fault, e bloquear refs-para-None antes do spawn. Um cluster coeso que mata os confirmados #3, #4, #5, metade das suspeitas, e — crucialmente — impede a library de certificar composto quebrado como template (protege o loop de self-improvement inteiro, Milestone J).

2. **Lifecycle de cancelamento/timeout + liveness guard.** Flag de cancel checada pelo engine por node, `core.cancel(sub_id)` no timeout do collect, timeout de rede nos clients, `shutdown` não-bloqueante com `cancel_futures`, e rejeição de `resume_run_id` não-terminal em `start()`. Mata o critical (#1), os dois zumbis (#2, #7) e o cancel-que-não-cancela (#6) — e é pré-requisito para qualquer resposta futura a rate-limit (o único "no" do scorecard).

3. **Superfície de ensino da tool.** Incluir `SpecIssue.example` no erro de validação, enumerar os 7 node-types com campos + 1 exemplo compacto no RUN_GUIDANCE, validar stage/branch dicts (dispatch por type ou exigir `prompt`), e rejeitar os campos hoje declarados-mas-ignorados. Barato, sem risco de runtime, e é o que separa "converge via loop de reparo" de "acerta de primeira" — a capacidade #1, que é a razão de ser do harness.
